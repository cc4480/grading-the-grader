SecScan product report

SecScan (secscan.us) scans a live website from the outside and grades it A to F. It is aimed at apps built with AI tools such as Lovable and Bolt. There is one kind of scan, the full one: it makes 143 checks across 41 tests, sends test traffic only to domains the user has proven they own, and can watch sites continuously. Every account gets 3 free scans a month. Paid plans start at $19 a month, but payments are switched off.

What a scan is

Three words are used for counts, and they are not interchangeable. A test is one thing the scan records in its log (41). A check is one detection inside a test (143, the number the product advertises). A finding name is a distinct title that can appear in a report (310 in the generated index), because one check can report several variants. One path probe covers 78 paths and one secret scanner covers 35 patterns, so these numbers differ by design.

One scan type

The old Basic and Deep tiers are gone. The scan route sets every scan to the full run, and the API still accepts "deep" only so old clients keep working. What changes from one scan to the next is how much of the target the scanner is allowed to reach: proof of domain ownership, credentials, a second account, an out-of-band collector, a GitHub repository, and one opt-in test.

What happens during a scan

  1. Passive analysis. One request to the target, then headers, cookies, HTML, JWTs, structured data and technology fingerprints are analysed.
  2. Probes in parallel. Sensitive files, email and DNS security, source maps, API docs, cloud storage, GraphQL, Supabase and Firebase, JavaScript secrets, a crawl of up to 20 pages, known CVEs, and more, depending on the access level below.
  3. Worker checks. A TLS grade from Qualys SSL Labs, plus reconnaissance: DNS records, subdomain enumeration over 64 common names, and a port scan of 33 ports (the port scan needs a verified domain).
  4. Report. Findings with severity and confidence, a score and grade, an AI-written analysis (or a built-in template when the AI is unavailable or switched off), and a log of every test with the reason for any that did not run.

The score is the sum of points, capped at 100, and lower is better. SecScan's scale is the opposite of Seclayer's, so the two numbers are not comparable. A scan that a bot-protection layer answered is not graded at all: the grade is an "incomplete" marker, because the score would otherwise read as a perfect 0.

What runs at each access level

The gate is one function (activeProbeGate.ts). Active tests run only when the user has proven ownership of the target's domain by a DNS TXT record or a well-known file. The gate fails closed: any error while looking up the verification counts as "not verified". An operator setting can unlock it on a private instance, and a development flag can do so outside production. Tests that do not run are listed in the report as "not tested", with the reason. In total, 17 of the 41 tests (50 of the 143 checks) need a verified domain, so an unverified scan runs the rest.

Inputs and safety rules

What a scan can be given

  • A URL. Public http or https only. Private, local and link-local addresses are refused before anything is queued, and checked again on every request and every redirect.
  • Credentials. A session cookie or bearer token, or a sign-in through the site's own login form using a headless browser. Needs a registered, email-verified account. Stored encrypted, decrypted only inside the worker for one scan, then discarded. Sent only to requests aimed at the target and dropped on any redirect away from it. A form login can sign back in if the session expires; a pasted cookie cannot, and the report says which happened.
  • A second account. Supplied as a pasted session or as a username and password, or created automatically (the automatic second account option needs first-account credentials). Unlocks the cross-account access-control test.
  • A GitHub repository URL. Public repositories are searched for committed secrets. A private or missing repository shows as "not tested".
  • The race-condition opt-in. Off by default, needs a signed-in test account.

What the scanner will not do

  • It never sends a request whose success changes customer data. Authentication coverage uses GET and HEAD only, because an unauthenticated POST sent to see whether it is rejected performs the write when the answer is "no".
  • Body injection is limited to read-shaped endpoints (search, query, filter, report, graphql). Write-verb authorisation is tested against an identifier nothing can exist at. PUT is never sent. Mass assignment is read from the declared API contract, never probed.
  • The Supabase write probe uses a field that cannot exist in any real schema. If a row is created anyway, it is cleaned up immediately.
  • Out-of-band URLs point only at SecScan's own collector, never at an internal range or a cloud metadata address.
  • A destructive-action guard keeps the crawler and injection probes away from URLs that read as delete, cancel, revoke or log out.
  • The scanner identifies itself as SecScan-Security-Bot/1.0 with a link to secscan.us/bot, a plain page for site owners who see it in their logs.

The report

  • Live scan terminal. A replay of the scan test by test with each check's outcome. A check shows "clear" only when that is certain; otherwise it shows "checked". Tests that did not run are listed last under "Not tested on this scan".
  • Findings with severity, confidence, evidence, and filters. Categories use one colour palette across terminal and report (38 categories in 11 families).
  • Reproduce steps. A curl replay, shown only when the evidence is a plain GET, HEAD or OPTIONS request. Nothing is guessed.
  • Fix prompts that know the platform. Ready-to-paste prompts for Lovable, Bolt, Next.js, WordPress, Supabase, and (per the build report) Shopify, Wix, Squarespace, Webflow, Firebase, Vercel and Netlify.
  • AI analysis written by DeepSeek, with a built-in template as the fallback. A Settings switch stops findings from being sent to the AI provider; the report then says the analysis is off. Findings are redacted before sending.
  • Compliance mapping. Findings mapped to controls in SOC 2, PCI DSS, ISO 27001, OWASP ASVS, NIST SP 800-53 Rev. 5 and the HIPAA Security Rule technical safeguards. It is conservative and never a verdict: only an auditor signs off on compliance.
  • Changes since the last scan. New, fixed and unchanged findings. A finding counts as fixed only if its test ran again; otherwise it is "not re-checked".
  • Verify the fix. A free, limited re-scan (10 a day) judged against one finding. Fixed only if that test ran again; otherwise "could not be checked".
  • Dismiss a finding as not applicable, by the web app or the MCP tool, and restore it later.
  • Share link. A public, revocable link to a report. PDF and print export from the report page.
  • Coverage honesty. The report states when a bot-protection page answered instead of the site, when active tests were skipped, and when a sign-in expired mid-scan.

Monitoring

Monitoring re-scans a site automatically and raises alerts. It is sold as part of the plans (3 sites on Starter, 5 on Pro) and is gated by a setting (MONITORING_REQUIRES_PLAN) that the go-live checklist turns on.

JobScheduleWhat it does
Adaptive rescanSweep every 6 hours; per site every 14 days at grade A, 7 at B or C, 3 at D or FFull scan, compared with the last one to find regressions. The cadence reacts to the grade.
PulseHourlyOne request and one TLS handshake: is it up, is the certificate valid, has anything visible changed (headers removed, HSTS weakened, TLS downgrade, final URL changed). Down alerts need two consecutive failures. Pulse rows are kept 30 days.
CVE checkHourlyMatches newly published CVEs against the software detected on each site.
Certificate expiryDaily at 07:00 UTCAlerts before the TLS certificate lapses.
  • Alert kinds: new CVE, regression, certificate expiry, scan complete, availability, header drift. Each can be muted by kind and by minimum severity.
  • Channels: email, and a webhook that sends Slack-compatible JSON (works with Slack, Discord's Slack endpoint and Teams incoming webhooks), retried once on failure.
  • Per site: history, score history, regressions, pulses and alerts; pause and resume (nothing is deleted); a "scan now" that draws on the same allowance as any scan.
  • Scans the scheduler starts on its own do not spend the user's free scans.

How many times the 30-site list was run

The exact answer from the stored data, since the number matters:

  • 5 complete passes of all 30 sites are stored as raw output: 2026-09-08, the 09-10 38-target re-scan (which contains all 30), 09-24, and two on 09-30 (before and after that day's fixes).
  • 10 rounds included at least one of the 30 sites: those 5, plus two 20-target sweeps (09-10 and 09-19), the 20 guard targets (09-30) and the 14-target technology sweep (09-30), all stored, plus the 09-12 pre-marketing sweep, which the audit documents but whose raw output was not committed.
  • Each of the 30 sites has between 5 and 9 stored scans (190 in total). The busiest is npmjs.com (9), then 11 sites scanned 8 times.
  • Repeats that are not in the stored files: nasa.gov was scanned ten more times to catch an intermittent false "Missing SPF Record"; reddit.com's CSP finding was re-fetched in repeated batches (four repeats of seven paths, six repeats of three); the 09-07 fixes were verified over three rounds across five sites, and over 15 sites for the bot-protection fix.

So "the 30 URL test at least 10 times" holds as 10 rounds that included the list, but the complete 30-site list as a single pass has been stored 5 times.

How every finding was checked

  • Against the live response, with the scanner's own user agent. Targets answer a browser and a scanner differently, and that difference is where the mistakes hide. Google serves its NID cookie without Secure to a scanner and with it to Chrome, so checking in a browser shows the opposite of what the scanner saw and nearly got a correct detector removed.
  • Repeated, through the scanner's own fetch layer, because a plain curl is sometimes refused (reddit answers it 403) and a single observation can be a flap.
  • Independent re-derivation. On 09-30 every header finding (CSP present or weak, nosniff, clickjacking, base-uri, cookies, the HTTP redirect) was recomputed by a separate fetch and compared. It agreed on every one. DNS findings were checked against Cloudflare and Google resolvers.
  • A written "checked and correct, do not fix" list for each round, so a true finding that looks false is never deleted again.
  • A clean twin for every fix. Each fix has a test that fails on the old code, and a test that the real problem is still found.
  • A code review of every probe family (09-30). Six reviewers fed the real functions realistic benign responses through a mocked fetch, looking for any finding that fires on a healthy site. Every item was reproduced before it was fixed.
  • A target whose faults are known exactly. The vulnerable-app gate plants the faults, and the clean twins check the same code against the safe version.

Ground truth and benchmarks

  • Planted-flaw check. detection-check.ts plants 19 flaws and returns 34 findings. The 15 it never asked about were checked by hand, including the Nginx 1.14.0 and PHP 5.6.40 end-of-life matches, which were true of what the fixture serves.
  • Vulnerable-app gate. The real scanner (passive, active and signed in with two accounts) is pointed at a fixture whose faults are known, and must find 82 of 82 with no false alarms. Every new check ships with a vulnerable case and a clean twin.
  • Head-to-head benchmark (detection, not false alarms). Against the same fixture with 74 known faults, blind adjudicators scored SecScan 68 of 74, OWASP ZAP 18 to 19, and Nuclei 7 to 8. The adjudicators agreed on 95.9% of calls (9 disagreements). The benchmark also caught SecScan's own unfairness: it found faults at paths only its wordlist knew, so the fixture now links real features from its navigation. The authors say plainly that this is not independent verification.
  • Automated tests. 686 passed on 2026-09-08 with 12 new regressions for that day's six bugs. 2,611 pass today. Test fixtures themselves were a cause: one helper built DNS answers with no record type, which made the CNAME-as-MX bug impossible to express.

Not verified or still open

  • The 09-24 round did not re-check its 82 medium and low findings, and the 09-30 round did not re-check technology fingerprints, CVE and end-of-life matches, or the JSON-LD notes.
  • Several fixes narrow a check on purpose, so a real problem in those shapes can now be missed: an app that renders the same record for any id, an unauthenticated DELETE answered 404 for a missing id, inner-route config files without credential-shaped keys, and a bucket whose first 100 objects are all static assets.
  • The "unclaimed resource" page texts for Vercel, Ghost, Tumblr, Readme, Heroku and GitHub Pages were written from memory of each provider's page, not fetched. No version floor exists for two 2026 nginx and Apache CVEs, and none was invented.
  • Technology rules for Google Analytics, jQuery, Lodash, Alpine and HTMX still match loosely. The 30-day certificate-expiry alert cannot tell a certificate about to auto-renew.
  • As of the 09-19 audit note, SSRF and the out-of-band collector had not been exercised by any sweep of a real site (the runner skips them). They are covered by the vulnerable-app gate. I did not check whether that changed after 09-19.
  • The audit recorded 80 actionable findings for the 09-19 passive round; the committed file counts 85 above Info. I did not reconcile the difference. For 09-24 and 09-30 the audit and the files agree (98 and 92).
  • The build report of 2026-09-26 lists "a full false-positive sweep" as still to do before launch. The 09-30 sweeps came after that note, and no final sign-off is recorded.
  • Bot-protected sites (npmjs, stackoverflow, apnews) answer this scanner with a challenge, so a scan of them tests nothing. The guard list swapped two of them for pypi.org and rubygems.org for that reason.

The same method was applied to Seclayer, SecScan's sibling product, on 2026-09-30: 38 real sites, 67 above-Info findings, each independently re-checked, one false positive found (a challenge page that echoed the request path) and fixed, and the report now states exactly why a blocked scan was judged blocked. Where the docs disagree with the code

These were found while building this report. The code is the source of truth, and each one is a claim a customer could read.

  • Check count. The code catalog has 143 checks in 41 tests. My notes said 140 (written 2026-09-26) and the coverage doc says "about 129 or more".
  • Tiers. SCAN_COVERAGE.md still describes Basic and Deep scans with approximate request counts. SCAN_TESTS.md and the route code say there is one scan type.
  • Secret patterns. The code array holds 35; the catalog and site say 34; the coverage doc says 32 in one place and lists 21 in another.
  • DKIM selectors. The code tries 42; the coverage doc says 30.
  • Finding names. SCAN_CHECKS.md (generated) says 310; the coverage doc says 279. The generated index also prints "probes-data is one path probe applied to 0 paths", a generator slip, since the code has 78 paths.
  • Sensitive paths. The coverage doc says "about 75"; the code has 78.
