Where it stands, 2026-09-22

Added when the pre-launch review was run. Below is the honest split: what has evidence behind it, and what is built and shipped but has never been observed working. The second list is the one that matters, because 2026-09-21 produced three separate bugs of exactly that shape.

The recurring failure has a shape, and it is not “the tests were missing”. Rate limiting had tests and was dead in production. The scan cadence had eight tests and had never once worked. The monitor page was saving data correctly and displayed none of it. In all three the unit tests passed, the types checked, and the feature did nothing — because each test exercised one half of a seam and nothing exercised the join. Read the second table below with that in mind: passing tests are not evidence that a feature works.

Shipped, but never observed working

Everything here typechecks, has unit tests, and is deployed. None of it has been seen doing its job in production, which — on the evidence of 2026-09-21 — is not a strong position.

No monitoring alert has ever been confirmed delivered Availability alerts have never fired Drift alerts have never fired Certificate expiry alerts have never fired Stripe never tested against a real endpoint CVE dedupe unexercised — nothing has matched yet

The alert-delivery gap is the important one. Six alert kinds, a severity floor, suppression handling, and both the email and webhook paths are built and unit-tested. Nobody has watched a single one arrive. All six monitored sites are up and unchanged, so the down, recovered and security_drift send paths have executed zero times; no monitored certificate is inside 30 days, so the expiry path has not run either. This is the last untested link in the chain, and it is the same shape as the three bugs above.

A note on what was not concluded: production logs were checked for email activity and showed none, but both containers had restarted 90 minutes earlier and no scan completed or alert fired in that window. An empty log window is not evidence of a broken mailer and was not recorded as one.

The cheapest real test is to point a monitor at a URL under your own control, remove a security header, and wait for the top of the hour. One run then exercises drift detection, the severity floor, bulkMailAllowed, suppression and Resend delivery together — precisely the seam that unit tests keep failing to cover.

How to read the score

computeRiskScore sums severity weights and caps at 100 — higher is worse. Critical 30, High 15, Medium 5, Low 1, Info 0. computeGrade: A ≤ 10, B ≤ 25, C ≤ 45, D ≤ 65, F > 65. Info findings score zero by design: a check that can only observe whether something is advertised — rate limiting, security.txt, DNSSEC — must not move a grade. That is why a 19-finding site can still grade C.

Reproducing any of it

# passive, all 20 guarded targets
DATABASE_URL=postgres://localhost/x \
  npx tsx artifacts/api-server/scripts/live-scan.ts --json sweep.json

# active, owned domains only — the flag carries its own allowlist
DATABASE_URL=postgres://localhost/x \
  npx tsx artifacts/api-server/scripts/live-scan.ts --active https://seclayer.app

DATABASE_URL only has to be set — the scanner module imports the db layer at load time and a passive scan never reads it. Raw output for every run is committed beside SCAN-RESULTS.md, so each row can be checked rather than taken on trust — and every finding from every run is now published host by host in the Corpus Findings appendix. Run the sweep before releasing scanner changes, and read the output rather than diffing it: the audit exists because six findings were "fixed" on suspicion and all six turned out to be real.

03

vuln-fixture — a target with faults known exactly

Real sites can only prove the scanner doesn't cry wolf. They cannot prove it catches everything, because nobody knows the ground truth of a stranger's server. So a second app was built specifically to have every fault the scanner checks for, planted on purpose — then the real scanner was pointed at it and every result checked against what was actually planted.

73 of 73 tracked findings detected — full active pass, credentialed, two accounts

Run via verify-vuln-fixture.ts against the real scanning engine — not a mock, not a unit test of the detection logic in isolation. It includes the credentialed API surface (missing-auth, BFLA, mass assignment, IDOR) and cross-account access control, which need two real logged-in sessions to be checkable at all. Exit code is non-zero on any miss.

The tracked count has grown as checks were added — 69, then 70, 71, and 73 as of 2026-09-20. The figure above is what the script itself reported on its last run, not a number carried over from an earlier version of this document, because that count has silently drifted here before.

deserializationProbe.ts — added 2026-09-20 Four Set-Cookie values on a crawled inner route, one per marker: Java, Ruby Marshal, Python pickle and a URL-encoded PHP object. Each is a real serialized object carrying {"user":"admin"} that decodes to the genuine magic bytes, not a string shaped to satisfy the regex — a fixture that matched the marker without being the thing the marker stands for would verify the regex and nothing else.

Known limits of what this proves

All 78 probes-data.ts paths are served correctly, but verify-vuln-fixture.ts only asserts a sample of roughly ten by name — checking all 78 individually would make the script itself the thing most likely to contain a typo. The full list is cross-checked structurally instead, diffed against the source path list on every edit. "Present" is not the same guarantee as "this exact one was independently confirmed to fire", and this document does not pretend otherwise. Rate limiting and BFLA also depend on endpoint and burst budgets: if those change, the verify script must be re-run rather than assumed.

04

Real bugs this process actually found

Not hypothetical review comments. Each of these produced a wrong report on a real or fixture target, was root-caused, fixed, and pinned with a regression test. They are grouped by what kind of wrong they were, because the two kinds fail differently: a false positive is disputed by the customer, a false negative is never noticed by anyone.

False positives

False positive · 2026-09-07

Bot-protection page mistaken for the site itself

stackoverflow.com and npmjs.com returned a Cloudflare interstitial instead of their real page. Every content-derived check — CSP, cookies, headers, SRI, inline scripts, technology fingerprint, structured data — was describing the challenge page, not the customer's site. The report read as a scan of the customer and was a scan of a WAF error page. A recognizer now identifies the interception from vendor fingerprints and reports it once as a coverage note. Detection is strict on purpose: calling a real page a challenge page would suppress genuine findings, which is worse than the bug being fixed. A large document that merely loads a bot-protection script is not a challenge, a 403 returning a real access-denied page is not a challenge, and the words "just a moment" in body copy are not a challenge.

False positive · in the fix itself

nytimes.com flagged as intercepted — on a header set for allowed traffic

The new interstitial detector matched x-datadome: protected by presence. DataDome sets that header on traffic it lets through, not traffic it blocks. The real 1.3 MB homepage, two JSON-LD blocks and all, was sitting in the response body the whole time. Fixed by matching the header's value rather than its presence; a regex is now required on every header signal so the shortcut cannot be taken again. This is the audit's recurring error — reading the presence of a response as the meaning of the response — reappearing inside the fix for a previous instance of itself.

False positive · 2026-09-08

GOV.UK's email domain resolved wrong — three bugs behind one HIGH finding

toEmailDomain derived the email domain by counting label lengths: uk is two characters and gov is three, so it took the .co.uk branch and, with only three labels, returned the hostname unchanged. SPF was looked up at www.gov.uk and DMARC at _dmarc.www.gov.uk, neither of which exists. Separately, dnsQuery returned the whole DoH answer section without filtering on record type, so an MX query answering with two CNAMEs was read as "this domain actively sends email" and escalated the finding to HIGH. And the evidence string hardcoded Status: NOERROR (domain exists) regardless of what the resolver actually returned.

The target was the single most email-secure domain a UK scan is likely to encounter — v=spf1 -all at gov.uk and p=reject at _dmarc.gov.uk — and it was reported as having neither. Fixed by walking the ancestor chain, filtering DNS answers to the type actually queried, and suppressing the finding on NXDOMAIN. toEmailDomain was deleted rather than patched: guessing a registrable domain from label lengths is what produced the failure in the first place.

False positive · introduced and fixed in one round

DNSSEC "not enabled" on a properly signed zone

Introduced by the record-type filter above. DNSKEY records live at the zone apex, and checkDnssec asked the scanned hostname: www.nasa.gov answers with one CNAME and no DNSKEY, while nasa.gov is properly signed. Before answers were filtered by type, that CNAME had been counted as a DNSKEY and the check passed for entirely the wrong reason — a hidden false negative that the filter converted into a visible false positive. The corpus went from 13/30 to 26/29 in a single run, which is what made it obvious. Now walks to the apex. This is the argument for re-running the corpus after a fix rather than trusting a green suite.

False positive · 15 of 30 sites

"No rate limiting detected" asserted something a passive GET cannot observe

stripe.com sends no rate-limit headers at all and unquestionably rate-limits. Rate limiting lives on login and API routes, not the homepage, and CDNs throttle silently. The infrastructure allowlist had already been patched twice — Google server tokens, then GitHub's edge — which is the shape of a check chasing an unobservable property one vendor at a time. Renamed to Rate Limiting Not Advertised in Response Headers and dropped to INFO at weight 0. Note the contrast with the active rate-limit check in Round 5, which earns its severity because it sends the requests and reports what came back.

False positive · 2026-09-10

GraphQL match on the literal word "graphql"

nytimes.com's SPA catch-all served 1.25 MB of plain HTML at /ca/graphql, and the probe matched the word in the URL. It now requires GraphQL-shaped JSON or a playground fingerprint before reporting. Effect on that run once fixed: 28 → 23, grade C → B.

False positive · 2026-09-10

"PHP error" match on a bare word and a colon

linkedin.com — a Java site — was reported as leaking PHP errors because the pattern matched JSESSIONID loosely. Made structural rather than a bare substring match. Effect once fixed: 20 → 15, grade unchanged at B.

False positive · 2026-09-12

Permissive crossdomain.xml on a site that permits nothing

Fired on <site-control permitted-cross-domain-policies="all"> while the finding's own description claimed "access from all domains (*)". nytimes.com has no bare domain="*" — every allow-access-from is scoped to *.nytimes.com. permitted-cross-domain-policies="all" is a meta-policy governing whether sub-path policy files may exist, it is Flash's own default when the element is absent, and with Flash EOL since 2020 it warrants no medium CORS finding. The check now fires only on a genuine domain="*".

False positive · 2026-09-12

An exposed OpenAPI spec reported as a mistake

The evidence ("spec structure validated") only confirmed the spec was real, never that exposing it was an error. Publishing an OpenAPI spec is mainstream intentional practice — Cloudflare's is literally titled "Cloudflare Public Site API" — and the endpoints it documents still enforce their own auth, so the spec describes the surface rather than opening it. Reclassified: a spec file is INFO ("confirm this is intended"), an interactive "Try It Out" UI is LOW.

False positive · caught before shipping

Mail server "does not offer STARTTLS" — on one that does

The one false positive in this audit that was never released, because it was found by pointing the new detector at known-good targets before committing it. cloudflare.com's MX advertises STARTTLS on port 25 and presents a valid certificate. The detector probed 25, 587 and 465 and gated its finding on whether a port was reachable; Cloudflare's MX completes the TCP handshake on 587 then resets before answering EHLO, so starttlsAdvertised stayed null — the probe learned nothing, and silence scored as "no STARTTLS". Worse, it fired on some runs and not others depending on when the reset landed, which is the kind nobody disputing the report can reproduce. Fixed twice over: only ports that actually answered EHLO count as evidence, and the probe now checks port 25 alone, since an MX is an inbound relay and 25 is where every message from the world arrives. Scan cost fell from a flat 6.1s to 0.3–2.0s.

False negatives

False negative

A crashed check looked identical to a clean pass

Every one of 17 probe families was wrapped in .catch(() => []), so a check that threw returned the same empty result as a check that ran cleanly and found nothing. A transient network blip on archive.org silently erased a genuine missing-HTTPS-redirect finding with zero trace in the report. Fixed by tracking failures by name and emitting an explicit "N check groups could not be completed" coverage finding — deliberately an INFO note about the scan, never a vulnerability claim about the site.

False negative

The same swallowing bug, one stage later — found while validating SSRF coverage

The fix above covered the passive probes and stopped one stage short: API surface discovery, API endpoint testing, SSRF and cross-account access control each still had their own .catch(() => []). SSRF is where this mattered most — its entire method is a negative result ("no callback arrived"), so a failed out-of-band registration or a mid-scan network fault looked exactly like a target that genuinely is not vulnerable. Found not from a report but from reading the code one page down from where the first fix ended, while working out how to validly test SSRF at all. All four stages now report into the same coverage finding as the passive probes.

False negative · live in production

Daily CVE matching silently matched nothing for the stack that matters

Covered in full in section 08. scanner.ts enriches detected technologies with versions for display — its own comment reads "Nginx" → "Nginx 1.18.0" — while the monitor's keyword table is keyed on the bare name and the lookup was exact. Every technology whose version the scanner successfully detected dropped out of CVE matching, with no error and no log. The seven that get enriched are Angular, Apache, IIS, LiteSpeed, Nginx, OpenResty and PHP: precisely the server-side stack a CVE feed exists for.

False negative · live in production

CVE-2025-48757 stopped being detectable, silently

Covered in full in section 06 — found by standing up a real Supabase project with Row Level Security deliberately off. The check that the whole feature is named after had stopped working for every current Supabase project, because Supabase changed the endpoint it depended on. This is the single most consequential finding in this document, and it was only reachable by using real infrastructure.

Caught by checking the deploy rather than the diff

Broken in production for minutes · self-inflicted

Not a detection error, but the more serious defect

Data exposure in report evidence

Inner-page cookie findings were quoting the cookie's value

SCAN-RESULTS.md stated that Set-Cookie values in committed runs "are replaced with <redacted>; names and flags are untouched, which is all the cookie findings are derived from." The committed file did show that — but nothing in the repository performed the redaction, so it had been done by hand, and a fresh run carried real fid=, loid= and session_tracker= values in full.

That matters well beyond these artifacts, because report evidence is durable and shareable: it is stored in the reports table, rendered into the emailed PDF, and readable by anyone holding a share link. On a credentialed scan the scanner is signed in, so the value being quoted is a live authenticated session token. crawler.ts was the only path doing it — scanner.ts already reported root-page cookie findings by name alone and deserializationProbe.ts redacts explicitly — so this was an oversight in one of three sibling paths rather than a decision. redactCookieValue now replaces the value and keeps every attribute. The claim in the results file is now true by construction rather than by hand.

The pattern across almost all of these: reading the presence of a response as the meaning of the response. STARTTLS read reachability as an answer; the WAF detector read a header's presence as "blocked"; security.txt reported "not found" regardless; the DNS checks read answers without checking what they were. An evidence string is a claim that can be checked — and if it points somewhere the scanner did not actually look, it does not merely fail to support the finding, it argues against it.

Concurrency and load — against the live pipeline

The last item that had never been attempted, and the only one that was a decision rather than a resource gap: it means deliberately pushing real traffic through production. Run 2026-09-20 against the live scan pipeline on secscan.us.

How it was set up, and what it deliberately did not do

Target was seclayer.app — owned, and on separate infrastructure — so the box being scanned was never the same box doing the scanning, which would have confounded every number below. No production configuration was changed. No environment variables, no rate limits, no database writes. The burst was built to fit inside the limits that are already live rather than to lift them: ten accounts registered through the ordinary public signup API, two scans each — the existing default free-scan allowance — for twenty concurrent submissions, comfortably under the 40-per-hour per-network ceiling.

Twenty rather than the twenty-five to thirty originally intended, because the registration endpoint carries its own anti-abuse limiter of ten per fifteen minutes per address. Defeating an abuse control to make a test number look rounder is not a trade this document is willing to record, so the burst was sized to the limiter instead.

What it confirmed

Confirmed — backpressure

The worker caps itself at 8 concurrent scans and queues the rest

scanConcurrency=8 is logged explicitly at boot, and the burst made it observable: exactly eight jobs moved to "scanning" immediately and the remaining twelve waited for a slot. Accepting work quickly and then metering it is the right shape — the submission path stayed sub-second under a burst two and a half times the worker's capacity, and nothing queued was dropped.

Confirmed — the verification gate holds under load

Twenty unverified accounts could not aim active probes at a third party

Every one of the twenty scans logged Domain not verified for this user — running passive checks only. This is the control that stops the platform being used as an anonymous attack proxy, and the burst is the first thing to exercise it at concurrency: ten freshly-created accounts, none of which had verified anything, could not collectively turn the scanner on a target. Had it failed open, the test itself would have hit seclayer.app with twenty simultaneous active probe runs.

Confirmed — graceful external degradation

SSL Labs timed out on all twenty and cost nothing but the grade

Every scan logged [ssllabs] Assessment timed out after 30000 ms — continuing without TLS grade and fell back to basic TLS detection. Twenty near- simultaneous assessment requests against a free third-party API is exactly the condition under which that dependency should be expected to refuse, and the pipeline treated it as best-effort rather than as a scan failure. A slow external dependency degrading a single field, instead of failing the whole job, is the behaviour worth having.

What it found — a real production bug

Bug found and fixed · deployed 391857a

A scan whose owner deleted their account kept running, and kept spending

The test script deleted its ten disposable accounts immediately after submitting, while the scans themselves take minutes. The result was unambiguous: 18 of the 20 scans ran to completion, made a billed DeepSeek AI call, and then failed at the final report insert — a foreign key violation, because reports.scan_id references scans.id and deleting an account removes its scan rows first. The work and the money were spent on a report that could never be stored and nobody could ever read.

The premature cleanup was a flaw in the test script, not a realistic user sequence. But the path it exposed is entirely realistic: a user who starts a scan and then deletes their account from Settings — which the product offers, and which takes seconds — lands in exactly this code path. The twelve scans queued behind the concurrency cap were the worst case, deleted long before a worker slot even freed up, and scanned in full anyway.

The fix. Both status updates that already bracket the expensive work now return their affected rows, which makes the existence check free — no additional query. Step 1 abandons a job whose scan row vanished while it sat in the queue, before any scanning happens at all. Step 3 abandons one that lost its row mid-scan, immediately before the only step that costs money. The remaining window — an account deleted during the AI call itself — is seconds wide instead of the whole scan, and still lands in the pre-existing catch that fails the scan cleanly rather than crashing.

Why the guard is safe. routes/scans.ts commits the scan row before enqueueing the job, so a missing row always means a deletion and never a job that overtook its own insert. This was checked rather than assumed, because a guard that aborts healthy scans would be far worse than the bug it fixes.

Pinned by three tests, and — more to the point — the two guard tests were confirmed to fail with the guards disabled, and the third test asserts the healthy path still runs end to end. A regression test that passes with and without the fix protects nothing, and this document has no way to tell the difference after the fact unless someone checks at the time.

What this test did not measure. Twenty concurrent submissions against an eight-slot worker exercises queueing, backpressure and the failure paths; it does not establish a throughput ceiling, and no attempt was made to find the point where the pipeline actually degrades. Sustained load, multi-hour soak behaviour, memory growth across hundreds of jobs and behaviour with the queue deeply backed up all remain unmeasured. This is a correctness-under-concurrency result, not a capacity number, and it should not be quoted as one.

Cleanup

All ten accounts were deleted through the product's own DELETE /account endpoint, which cascades to scans, monitor subscriptions, report shares, dismissed findings, domain verifications, credits, auth tokens, pending logins and every session for that user — confirmed 10 of 10. No production configuration was modified at any point, so there was nothing to revert. The disposable Redis service from section 06 and its public endpoint were destroyed and confirmed unreachable.

08

Continuous monitoring — audited, and it was not working

Monitoring had never been tested. Around 1,240 lines across monitorScheduler.ts, cveMonitor.ts and routes/monitor.ts carried no test file at all, and no round in this document had ever exercised it. It is also a marketed feature: risk-adaptive rescans, daily CVE matching, certificate-expiry alerts, regression detection and webhooks are all described on secscan.info. Audited 2026-09-20.

The daily CVE job was matching nothing for Apache, Nginx, PHP, IIS, Angular, LiteSpeed and OpenResty

Not degraded, not noisy — silent. It ran every day, found nothing for those technologies, created no alerts, and logged no error, while every monitored customer running one of them believed they were covered.

The defect

scanner.ts:561-571 enriches each detected technology with its version for display. The comment on that block states the transformation outright: 

// Detect technologies and enrich with version numbers where available
// e.g. "jQuery" → "jQuery 1.11.3", "Nginx" → "Nginx 1.18.0"

cveMonitor.ts then looked those strings up in a keyword table keyed on the bare name, with an exact lookup and a bare continue on miss. There is no fallback and nothing is logged, so a miss is indistinguishable from a technology with no CVEs: 

const keywords = TECH_KEYWORDS[tech];   // "Nginx 1.18.0" → undefined
if (!keywords || keywords.length === 0) continue;

Proven by running the real matcher, not by reading it

matchCvesToTechnologies(["Nginx"],        [nginx CVE])  → 1 match
matchCvesToTechnologies(["Nginx 1.18.0"], [nginx CVE])  → 0 matches

Same CVE, same function, same keyword table. The only difference is the version suffix the scanner itself adds.

The inversion is the part worth keeping in mind. The seven technologies that get version-enriched — Angular, Apache, IIS, LiteSpeed, Nginx, OpenResty, PHP — are the server-side stack CVE monitoring is worth running for. The better the scanner did its job, the more certainly monitoring stopped doing its own. And version disclosure is most likely on old, unpatched servers that still expose Server: and X-Powered-By by default, so the feature failed hardest on exactly the targets that needed it. What kept matching were platform entries like Cloudflare, Vercel and Netlify — where a keyword hit on CVE prose means least.

Fixed — 9f17de7

The lookup now strips a trailing version-shaped token, and reports the technology verbatim so the alert keeps the version it saw. Only a trailing version is removed: splitting at the first space would turn "Ruby on Rails" into "Ruby" and "AWS CloudFront" into "AWS", trading one silent miss for another. A second fix re-keys "Express" to "Express.js", which is the string techFingerprint.ts actually emits — as "Express" that entry could never have been hit either.

14 tests, the first this module has ever had. The five covering the defect were confirmed to fail with the fix reverted, and the nine that do not depend on it kept passing — which is what distinguishes a regression test from a test that happens to be green.

Two limits pinned rather than fixed

Both are properties of keyword matching rather than bugs in it, so they are asserted by tests that document them — if either is ever tightened, the change is deliberate and those tests are what flag it.

No version awareness Matching is on the CVE's prose, so a current, patched nginx still matches a CVE about an old one. cveCheck.ts does real version-range matching during a scan; the monitor does not use it. An alert must therefore never be worded as "your version is vulnerable".
Generic keywords Entries like "php", "angular" and "railway" are matched with a bare substring test against the description. "railway" is an ordinary English word that appears in rail and ICS advisories — the same bug class as the linkedin "PHP error" and nytimes "graphql" false positives in section 04.

Rescan cadence — tested, and it holds

The cadence is a published claim: secscan.info tells people an A is rechecked every 14 days and an F every 3. It decides how often monitoring spends a customer's scan budget and sends traffic at their site, and it had no tests. It does now — eight, covering the published numbers, the fall-through for grades outside A–F, and computeNextScanAt's arithmetic across a DST boundary. All pass against current behaviour; nothing was broken here.

One of them asserts a property rather than the numbers: cadence must be monotonic in risk, so a worse-graded site is never rescanned later than a better one. That survives someone retuning the intervals, which the literal values would not.

One open question, pinned rather than changed. A scan a bot-protection layer answered is graded "N/A", and nextScanDelayDays falls through to the 3-day branch for it — the most aggressive cadence there is. A target that blocks the scanner will keep blocking it, so this spends a scan every three days, indefinitely, to learn nothing each time. It is not obviously wrong in either direction — retrying sooner is reasonable when a scan produced nothing — so it is a product decision, recorded in a test that will catch any change rather than quietly re-tuned here.

Still untested in this feature

CVE matching is fixed and the cadence is tested. The rest of monitoring remains unexercised: the 6-hourly sweep that acts on that cadence, certificate-expiry alerting at the 30/14/7-day thresholds, regression detection, webhook delivery, and the 600 lines of subscription routes. One correction found while reading the cert-expiry job, and fixed: its comment claimed the loop fires "the lowest applicable" threshold, while the array order [30, 14, 7] means the break fires the widest unalerted band first. The behaviour is sound — the email quotes the real days-remaining either way — but the comment described the opposite of the code, which is how a later reader talks themselves into "fixing" a working check.

The two decisions that make it usable rather than unbearable

Header presence is fingerprinted, never values A Content-Security-Policy carrying a per-response nonce differs on every single request. Hashing values would report drift every hour on precisely the sites doing CSP properly — and an owner who gets a false alert hourly turns it off, including on the day it is true. HSTS max-age is the one tracked value, because a header still present with max-age=0 has been switched off while looking untouched.
Alerts are deduplicated per (subscription, CVE) The 3-hour lookback deliberately overlaps the hourly schedule, because NVD populates a CVE's published timestamp before it appears in the feed. Without dedupe that overlap sends the same email and fires the same rescan 24 times a day. It also collapses one CVE matching two technologies within a single run — which a database check cannot catch, since the already-alerted set is read before any of that run's rows are written.
Outages are confirmed, not reported on sight A down alert fires only on the pulse that makes the run of failures exactly two long, so a four-hour outage sends one email rather than four, and a single dropped request at 03:00 sends none. A recovery is only reported if the outage reached that threshold — otherwise it would announce the end of an event the reader never heard about.
Redirects are followed by hand, guarded per hop redirect: "follow" would have undone the SSRF check the URL passed when the subscription was created: a target validated as public last month can answer today with a 302 to 169.254.169.254, and fetch would follow it before any of our code saw the Location header. Refusing redirects outright was not an option — monitored URLs legitimately redirect to www and to HTTPS.

And "social preview asset over HTTP" cannot fire at all, because the fixture runs on plain HTTP by design — the same class as the HSTS and Cache-Control exclusions already documented there.

Code with no test coverage

Monitoring internals — the 6-hourly sweep and cert-expiry thresholds Outbound webhook SSRF guard — closed 2026-09-20 routes/feedback.ts — closed 2026-09-20 Monitor route ownership — closed 2026-09-20

Section 08 fixed CVE matching and gave that module, the rescan cadence and the subscription routes their first tests. Section 09 then covered the cadence end-to-end and added 48 more tests around the hourly pulse and CVE dedupe. What remains untested in monitoring is delivery: the 6-hourly sweep body, the 30/14/7-day certificate thresholds, and every alert send path — email and webhook alike — which have unit tests but have never been observed reaching a recipient. The "N/A"-grade cadence question is pinned by a test but still unanswered as a product decision.

Monitor route ownership is closed. Six endpoints under /monitor/subscriptions/:id take an id straight from the URL — the exact shape of the flaw this scanner exists to find in other people's applications, where getting it wrong means one customer reading another's scan history and regression list. All six already did it correctly and identically: a lookup scoped by id and userId, then 404 rather than 403, so the response does not confirm that someone else's subscription exists. Nothing was broken.

The tests are written structurally rather than one per endpoint, because the realistic future bug is not someone breaking a handler that works — it is someone adding the seventh endpoint and scoping the lookup by id alone. A test that enumerates the router and holds every :id route to the rule catches that on the day it is written; six per-endpoint tests would all pass, because the new endpoint is in none of them. One further test asserts the enumeration actually found at least six routes, since a structural test that silently matches nothing passes while asserting nothing. Confirmed non-vacuous by removing the ownership constraint from the DELETE handler, which fails the suite and names that endpoint.

The outbound webhook SSRF guard is closed. A monitor subscription takes a webhook URL from the user and the server then makes requests to it — server-side request forgery by construction, and the exact class this scanner sells itself on finding in other people's applications. The control was already correct: https-only so a token in the URL cannot leave in cleartext, host rules imported from the same module the scan-target path uses so the two cannot drift, redirects refused outright rather than re-checked per hop, and the check running before anything is sent. Nothing was broken.

It is tested now because an SSRF guard fails silently by definition — a successful bypass looks exactly like a delivered webhook, so there is no symptom to notice and no error to read. One careless refactor is the whole distance between this control and no control. Ten tests assert it by its effect rather than its internals: whether a request was attempted at all. Loopback, RFC-1918, the cloud metadata address at 169.254.169.254, plain http on a public host and unparseable input are all refused; a legitimate Slack endpoint is delivered, which is what stops the refusals passing vacuously. Confirmed by replacing the guard with true, which fails all five refusal tests.

Regression detection is covered indirectly, and deliberately left there. It is a set-difference over finding fingerprints, and the property it depends on — that a fingerprint stays stable across rescans when only volatile values change — is already tested directly in fingerprint.test.ts, along with the non-idempotency trap that previously resurrected every dismissal naming a version, IP or port. Isolating the filter itself would restate that with more mocking and less meaning.

routes/feedback.ts is closed. It shipped on 2026-09-20 verified by a single manual POST, and now has fourteen tests: that an unauthenticated submission is accepted and stored with a null userId — the design decision the table was built around — and the deliberate asymmetry between what it refuses (empty, whitespace-only, missing body, over-long message) and what it tolerates (a rating outside 1–5, a fractional or wrong-typed rating, an over-long context, all clamped, nulled or truncated), because the message is the valuable part and a bad optional field must never cost one. They found nothing, which is the expected result for code that small; they were confirmed non-vacuous by removing the trim() and watching the whitespace test fail.

A known flaky test, recorded rather than tolerated

http.test.ts › "signs in once when several probes hit the expiry together" failed three separate times during this work and passed on every re-run, including three consecutive clean runs immediately after each failure. It is timing-sensitive — it asserts that concurrent probes hitting an expired session trigger exactly one re-authentication — and it trips under the parallel load of the full suite rather than on its own.

It is listed here because a flaky test is a real defect with a cost that is easy to under-rate: it teaches people to re-run a red suite instead of reading it. Every one of the genuine failures in this document was found by taking a red result seriously. A suite that cries wolf three times in a day erodes exactly the reflex that made the rest of this work possible. The check it performs is worth keeping — single-flight re-authentication is a real property — so the fix is to make the assertion deterministic rather than to delete it.

Deliberately out of scope

Throughput ceiling and sustained-load behaviour Multi-hour soak / memory growth across hundreds of jobs Per-finding confirmation of all 78 sensitive paths Mail-server STARTTLS against a non-resisting MX

Throughput and soak. Section 07 measured correctness under a burst, not capacity. Finding the degradation point means sustained traffic against production over hours, with real AI-call spend attached to every scan; it is a cost decision before it is a testing one.

The 78 paths. All of them are served by the fixture and the list is diffed structurally against the source on every edit, but only a sample is asserted individually by name — see section 03. The remaining risk is a typo in the fixture, not a gap in the scanner.

STARTTLS. Attempted and understood (section 06). Closing it properly needs an MX that does not drip-feed its banner as an anti-scanner measure. That is a different test with a different target, not a retry of the same one.

Not listed, and why: cloud storage, subdomain takeover, BaaS misconfiguration and exposed-service detection were all closed against real infrastructure (section 06). dnsChecks.ts is not listed either — real domains in the passive corpus, with genuine SPF, DMARC and DNSSEC states, exercised it without needing a purpose-built broken zone.

12

Payments — built and tested, deliberately left off

The instruction for this work was explicit: prepare the ability to charge, do not turn it on. What made that a real engineering task rather than a flag flip is that "prepare to charge" turned out to be two separate missing systems, not one — and finding the second one changed what "done" meant here.

Two gaps, not one — and shipping only the first would have been worse than shipping neither

Gap one, already known: nothing created a Stripe Checkout Session, so the webhook that credits an account (routes/stripe.ts) could never be reached by a real customer. Gap two, found while building the fix for gap one: even a successfully purchased credit could never be spent. POST /scans checked only the free-trial cap and returned creditUsed: false unconditionally — hardcoded, not computed. A customer who paid would have hit the same trial wall as one who hadn't, with their credits sitting in the database untouched. Building checkout alone would have taken real money and delivered a dead end; both were fixed together.

What was built

lib/credits.ts spendOneCredit, refundOneCredit, creditBalance. The spend is a single atomic UPDATE — balance - 1 WHERE userId AND balance > 0 — not a read-then-write, because two scans submitted together both reading "1" and both writing "0" is a lost-update race that gives one of them a free scan.
routes/scans.ts Spends a credit after the trial-exhausted check, then refunds it on every one of the six rejection paths that can still occur after a spend — invalid target, unverified email, bad credentials, and three more. A credit taken before validation and never given back on a later rejection is the same class of defect as the account-deletion bug in section 07: money and state going out of sync at a rejection path nobody was watching.
routes/checkout.ts GET /checkout/packs lists what's buyable with an enabled flag; POST /checkout/credits creates the real Stripe Checkout Session. Validates the requested tier against CREDITS_MAP, not PRICE_MAP — the map the legacy per-scan tiers still appear in but grant nothing from — specifically so a priced-but-uncreditable tier can never be sold.

Repricing, and why

The $2/scan pricing predated this work and was never re-examined against what it actually costs to deliver: DeepSeek's per-scan AI analysis runs roughly $0.002–$0.003 at current rates, so $2 sat near a psychological floor, not a cost one. Worse, both packs — 5 for $10 and 20 for $40 — priced out to exactly $2 per credit, while their own descriptions claimed savings ("save $85", "save $340") against a single-scan price that did not exist to sell. That claim was fiction from the day it was written.

But a pack's "X% off" description needs an actual single-unit price to be measured against, or it is the identical unbacked claim being fixed — so a real one-credit SKU was added. It is a two-line change (one map entry; the route already builds its sellable list generically from that map) but it is a product decision, not a refactor, and the user can veto it.

32 new tests, and one self-caught mistake

credits.test.ts (9) confirms the spend's balance > 0 predicate lives in the SQL WHERE clause rather than a JS check after a read. checkout.test.ts (17) confirms — among other things — that a tier priced in PRICE_MAP but absent from CREDITS_MAP is refused with 400, using the real retired basic/deep keys as the case. stripe.test.ts (6) pins the two maps to each other and to arithmetic — every sold tier is creditable, every pack beats buying that many singles, the largest pack has the best per-credit rate — rather than to today's specific dollar figures, so a future price change only fails a test if it reintroduces the same class of lie.

The first mutation-test run on stripe.test.ts was worthless, and it was caught before being reported as good. A perl regex meant to revert pack_5 to its old flat price silently failed to match — a whitespace/em-dash encoding mismatch — and left the file unchanged. The test "passing" after that was not a defense holding, it was a mutation that never happened. Caught by checking the file with grep before trusting the result, redone with the Edit tool, and confirmed for real: reverting pack_5 to $10 flat fails the per-credit-rate test and names the tier. This is the same failure mode as an earlier mutation test in this session, on a different file — worth recording twice, since it means the instinct to verify a surprising "pass" has to be permanent, not a one-time lesson.

What is still off, and what that means concretely

No paywall exists today, by design — nothing above changes production behaviour

STRIPE_SECRET_KEY is unset in production, so stripe is null: GET /checkout/packs reports enabled: false and POST /checkout/credits answers 503. The free trial is unchanged. The one live customer-facing copy referencing the old price — the email-capture panel a trial-exhausted user sees today — was corrected from a flatly wrong "$10 for 5 scans" to the new "$12 each, or $50 for 5", since a real signed-up user could hit that panel at any time regardless of whether checkout is wired to it yet. It is still the static fallback, not a working buy button.

Not yet tested against real Stripe, even in test mode. Every test above mocks stripe.checkout.sessions.create; nothing in this document has exercised a real Stripe API call, a real webhook signature, or a real completed checkout. That is the honest gap in this section — the code is correct by the same standard as everything else here, but "correct against a mock of Stripe" is not the same claim as "confirmed against Stripe," and this page does not have a Stripe-API item in section 06's table because no live key exists yet to test against. It belongs there the day one does.

The standard applied throughout

Every closure in this document had to clear the same bar, and the bar is worth stating plainly because it is the only thing that makes the rest of the page mean anything.

Run the real code The production detection path, not a mock and not a unit test of the logic in isolation. Where a test harness had to differ from production, section 06 says exactly how and why.
Against a real condition A genuinely open port, a genuinely exposed table, a genuinely dangling CNAME. A scan of a host with nothing wrong proves only that the scanner can stay quiet.
Confirm the target first The Redis instance answered PING before it was scanned; the Supabase table returned a real row before the probe ran. Otherwise a silent scanner and a silent target are indistinguishable.
Prove the test can fail The worker guards were confirmed to fail with the fix disabled. A regression test that passes either way defends nothing, and nobody can tell afterwards.
Close the window Every disposable resource — bucket, CNAME, Supabase project, Redis endpoint, test accounts — destroyed immediately after, and confirmed gone rather than assumed gone.
Record the shortfall Where a result is partial, inconclusive or narrower than intended, it says so on the page — the STARTTLS read, the port-number substitution, the burst sized to 20 instead of 30.
All three production bugs in this document exist only because of the second and third rules. The Supabase false negative, the account-deletion bug and the CVE matching failure were each invisible to code review, to the unit suite, and to any amount of scanning a healthy target. Each needed a real thing that was really broken — a live RLS-off table, an account deleted mid-scan, a technology string in the exact shape production produces — and each one was failing silently in production at the moment it was found. None announced itself; all three looked precisely like a system with nothing to report.
