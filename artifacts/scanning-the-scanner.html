A finding you can't reproduce is worse than no finding

A missed vulnerability costs you one finding. A false positive costs you the report — once a scanner has sent you chasing something that was never wrong, you have no way to know which of the remaining findings to believe. So we point the scanner at sites whose answers are already known, and read every finding that survives by hand. This is what that turned up in a day.

The method

Scan somewhere the answer is already known

Google, GitHub, Cloudflare and Mozilla run their security properly. On targets like those, a correct scan returns few findings and zero false ones — which makes every extra finding a lead worth pulling. Each one is checked against the live response by hand before a line of scanner code changes, including the findings that turn out to be right.

Why not just count findings?

Because the number goes the wrong way. A scanner that reports more is easy to build and impossible to trust. Every fix below reduced what we report on four of the best-secured sites on the internet, and that is the direction the number should move.

Found in the wild

Shipped, then caught

These were live and being shown to people. Each is fixed, each has a regression test, and each has its reasoning recorded so the fix is not quietly undone later.

Non-session cookie readable by JavaScriptgoogle.com

A flattened Set-Cookie header was re-split on commas. The comma inside expires=Tue, 09-Mar-2027 matched, shearing the cookie in half so every attribute after the date became invisible — including the HttpOnly the cookie actually carried.

Reach: any cookie whose expires= precedes its flags. That is most cookies on the internet.

CSP script-src contains a wildcardcloudflare.com · mozilla.org

The check matched any * anywhere in the directive, so ordinary allowlist entries like https://*.onetrust.com tripped it. Nearly every policy that loads analytics has one.

Reach: reported at High. The more carefully a site had written its policy, the more likely we were to call it broken.

No rate limiting detectedgithub.com

A header-absence check. GitHub enforces rate limits at the edge and exposes no rate-limit headers on HTML responses — so the absence of a header was being read as the absence of the control.

Reach: every site that rate-limits without advertising it, which is the normal configuration.

One cookie reported twicegoogle.com

Root-page cookies were analysed in one place and inner-page cookies in another, and the crawl's deduplication set started empty instead of seeded from the root scan.

Reach: a doubled finding count on any site that sets the same cookie on more than one page.

Missing security.txt — the evidence, not the findingmozilla.org

The finding was correct: the file is not RFC 9116. The evidence was hardcoded to read "not found" regardless of what the probe saw, so anyone who checked found a file returning HTTP 200 and reasonably concluded the scanner was broken.

Reach: a correct finding made to look like a bug. Evidence now reports what each path actually returned.

Found before release

Caught before shipping

Three never reached anyone, because a new detector is pointed at known-good targets before it is committed. The third is the one worth reading.

Mail server does not offer STARTTLScloudflare.com

The probe gated its finding on whether a port was reachable. Cloudflare's mail exchanger completes the TCP handshake and then resets the connection before answering EHLO — so the probe learned nothing at all, and that silence was being scored as a failure. Its MX does advertise STARTTLS, on a certificate valid for another 162 days.

It fired on some runs and not others, depending on when the reset landed. That is worse than a consistent false positive: whoever disputes the report cannot reproduce it, and re-running the scan appears to fix it. Only a host that actually answered EHLO now counts as evidence.

No Open Graph tags, no structured data, excluded from searchstackoverflow.com · npmjs.com

Every word of it true — of the Cloudflare "Just a moment…" interstitial those sites return to a scanner, which carries noindex,nofollow and no metadata at all. None of it true of the sites themselves.

And it is not one bad check. When an edge answers instead of the origin, every content-derived check describes the interstitial — headers, cookies, CSP, inline scripts, technology fingerprint — and the report reads as a scan of the customer's site while being a scan of a bot-protection page. A scan now says so once, plainly, and names which findings can no longer be trusted.

The third one

Then the fix made the same mistake, one level up

The detector written to catch bot-protection pages flagged nytimes.com as intercepted, on the strength of a x-datadome: protected response header. DataDome sets that header on traffic it has allowed. The real 1.3 MB homepage, both JSON-LD blocks and all, was sitting in the response body the whole time.

It is the same error as the STARTTLS probe and the rate-limit check before it: treating the presence of a signal as the meaning of the signal. Three times in one day, in three unrelated parts of the scanner, by people who had just finished fixing the previous one.

Header signals now match on the header's value, and the pattern is mandatory on every one of them — so the shortcut is no longer available to take.

The other half of the work

Findings that look wrong and are not

Half of a false-positive audit is deciding what to leave alone. Each of these was investigated, confirmed correct, and then written down as correct — because the obvious way to check them returns the wrong answer, and without the note someone eventually "fixes" a working check.

Non-session cookie missing Secure flag — NIDgoogle.com

Google serves NID without Secure to a non-browser client, and with it to Chrome. Open developer tools to check and you see the opposite of what the scanner saw. The finding stands.

Content-Security-Policy is report-onlygoogle.com

Only the Content-Security-Policy-Report-Only header is sent. A report-only policy enforces nothing — it is a measurement, not a control.

X-Frame-Options missing on 2 internal routesgoogle.com

Two policy pages return 200 text/html with no framing protection. They are not redirects, and the routes were verified individually.

Missing X-Content-Type-Options, Referrer-Policy, Permissions-Policygoogle.com

Genuinely absent from the response. A large, well-run site choosing not to send a header is still a site not sending the header.

Header findings on a health-check routegithub.com

The route really does return Content-Type: text/html with an HTML body, so the "HTML documents only" rule correctly includes it. Arguably over-severe for a static health page — but over-severe is a different argument from wrong, and the two get fixed differently.

For context

What is being audited

SecScan runs 127 distinct checks across 26 engine modules, which between them can produce 279 differently named findings — one path probe covers 78 paths, one secret scanner covers 32 patterns. Every scan runs every check; there are no tiers. The audit above covers the checks a passive scan performs against any site on the internet, which is the surface where a false positive is most likely to reach someone who did nothing to invite it.

Five more, from the same hunt

The eight above are the ones recorded against the four reference targets. Five further false positives were found the same day against other sites and fixed alongside them: a single-page app's catch-all response read as an exposed sensitive file, public infrastructure tokens treated as session credentials, technology fingerprinting firing on generic CSS class names and ordinary prose, a subdomain-takeover match on a live service, and a publishable API key reported as a leaked secret.

Every entry on this page is a real row from the false-positive audit kept in the SecScan engine repository, not an illustrative example. Findings counts are from live scans on 7 September 2026 and will drift as the targets change their own configuration — they are a record of a specific day's work, not a running scoreboard.

Named third-party sites appear only as scan targets. Nothing here describes a vulnerability in any of them; where a finding stands, it is a configuration choice those operators are entitled to make, and it is reported here to show what the scanner saw.
